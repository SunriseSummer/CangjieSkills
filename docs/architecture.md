# 技术架构

[← 项目说明](../README.md)

## 目标与边界

本项目把经过人工精炼和实战验证的仓颉知识交付给开发 Agent，同时控制首次读取量、后续检索次数和发布文件数量。核心约束是：

1. 维护者只编辑活动 Markdown 与 manifest；
2. Agent 只通过稳定的查询入口取用知识；
3. 开发态与发布态对同一查询给出等价结果；
4. 发布件不携带开发资料、测试、报告或 Markdown 文件树；
5. Tree-sitter 只提供解析恢复诊断，编译器负责最终语义裁决。

知识契约以仓颉 `1.0.5 (cjnative)` 和 stdx `1.0.5.1` 为基线。stdx 安装器可以适配其他工具链版本，但不会改变数据库内 API 的语义基线。

## 分层知识模型

知识树遵循严格的渐进披露结构：

```text
全局入口
└── 领域入口：语言 / std / stdx / 应用示例 / 工具链
    └── 主题或包索引
        └── 子主题索引或 API 类型成员表
            └── 细粒度特性、成员契约或完整示例
```

每一层都能独立支持决策：

- 全局和领域入口说明范围、边界与下级入口；
- 非叶子页面以精确摘要呈现整棵子树的能力，不用代码片段代替概念说明；
- API 类型页列出活动成员签名和一句话契约，普通用法通常止于这一层；
- 叶子页补充参数、返回值、异常、边界、互操作限制及必要示例；
- 应用示例以“场景分类 → 示例列表 → 完整项目或代码”组织，强调典型实现和最佳实践。

页面首行的 `cj-doc` 元数据保存稳定 ID、节点种类、层级和父节点。`guide-manifest.json` 与 API manifest 提供可验证的路由和检索字段，父索引维护面向人和 Agent 的入口表。

## 构建数据流

```text
references/*.md + manifest
          │
          ├─ build_search_index.py ──→ search-content.json.gz
          │
          └─ build_knowledge_db.py ──→ knowledge.sqlite3
                                          │
SKILL.md + 运行脚本 ─────── build.py ──────┴─→ .agents/skills/cangjie-coding/
```

`build.py` 是唯一构建入口，负责：

- 生成确定性的压缩路由索引；
- 同步发布态 `SKILL.md` 和必要 Python 模块；
- 核对 manifest、Markdown 页面和索引记录集合；
- 构建 SQLite 数据库并执行完整性校验；
- 使用暂存文件和原子替换，避免留下半成品数据库；
- 在 `--check` 模式下验证所有生成物均为最新状态。

数据库的逻辑哈希由规范化记录计算。相同知识输入会得到相同逻辑内容，便于发现意外漂移。

## 双后端检索

`scripts/doc_search/` 将查询解析、排序、节点解析、子树展开和输出格式与存储实现解耦：

- `MarkdownBackend` 用于开发态，读取 `references/`，修改知识后可立即验证；
- `SQLiteBackend` 用于发布态，以只读、immutable、query-only 模式访问数据库；
- 两个后端共享查询模型、确定性评分、展开限制和输出层，因此可做逐查询差分验证。

统一入口根据自身所在的 Skill 形态自动选择后端。调用者无需选择实现，也不应直接遍历 Markdown 或执行 SQL。

### 查询能力

- `--query` 可重复，一次进程批量处理多个独立意图；
- `--domain` 和 `--kind` 用于缩小范围；
- `--view indexes` 返回节点下全部非叶子页面正文；
- `--view leaves` 合并返回一个或多个节点下的叶子正文；
- `--node` 接受稳定 ID 或可解析路径；
- `--estimate` 在展开前报告页数和字符规模；
- 页数、字符数和宽节点保护避免无意读取整库；
- `--trace-file` 记录本地调用、命中和耗时，用于流程分析。

推荐路径是“批量摘要 → 最窄索引子树 → 选定叶子”。任何一层已包含完成任务所需契约时都应停止读取。

## 发布数据库

`knowledge.sqlite3` 包含四类数据：

- `documents`：节点层级、领域、种类、标题、摘要、路径、正文哈希及压缩正文；
- `signatures`：API 类型和成员签名，用于符号检索与成员表输出；
- `assets`：数据库内部的压缩路由索引资源，与项目目录无关；
- `meta`：schema、生成器、知识基线、记录数量和逻辑哈希。

发布查询脚本使用 Python 标准库读取数据库，不需要部署数据库服务，也没有迁移、连接池或写并发问题。SQLite 在这里是确定性只读文档容器，而不是运行期业务数据库。

## 发布边界

标准发布件仅包含：

```text
.agents/skills/cangjie-coding/
├── SKILL.md
├── references/knowledge.sqlite3
└── scripts/
    ├── search_docs.py
    ├── doc_search/
    ├── setup_stdx.py
    ├── stdx_setup/
    └── cj_ast.py
```

Markdown 知识树、构建器、验证器、测试数据、报告、README 和缓存均不进入发布件。相关回归测试持续看护该边界。

## 解析与编译验证

`cj_ast.py` 使用 tree-sitter-cangjie 提取 import、声明及 `ERROR/MISSING` 节点。此类节点表示解析器发生了错误恢复，适合快速发现简单片段的结构问题；宏 token、DSL 或语法树文法与编译器之间的差异可能产生假阳性，所以它不判断代码能否编译。

完整程序、类型解析、重载选择、宏展开、依赖配置、C FFI 和链接始终由 `cjc/cjpm` 验证。测试框架据此把简单行级示例与需要真实工程上下文的示例分开执行。

## stdx 安装机制

`setup_stdx.py` 检测 `cjc` 版本并选择兼容 stdx 发布件，默认安装到用户目录 `~/.cangjie/stdx/`。下载、校验、解压和项目配置被拆分为独立模块；安装过程使用跨进程锁、唯一暂存目录和原子提交，多 Agent 并发时复用同一份完整缓存，不互相覆盖项目或留下损坏安装。
